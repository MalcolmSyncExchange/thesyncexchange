# Artist Desk — Phase 0/1 baseline and security harness

**September 15, 2026 · Review only; no architecture schema or UI implemented.**

## 1. Outcome

Live metadata access was available for both Supabase environments. Production's application-domain schema matches the fully replayed repository migration chain at `4e47997b7bb71af443660ccd4032d12fd43bf269`, including the later role and track guards. **Migration history is incomplete, and storage policies differ materially from the repository.** Security staging has additional reviewed-rights and referenced-media protections not present in production or the deployed branch.

The regression harness runs actual PostgreSQL policies/triggers in an isolated in-memory database and executes current server handlers with mocked external dependencies. Known gaps are reproduced explicitly. A separate security gate fails on five required outcomes; a green characterization suite does not authorize a release or certify the new architecture.

No live INSERT, UPDATE, DELETE, DDL, migration, seed, auth signup, payment, storage mutation, deployment or environment change was performed. No real account was deleted. Live reads were catalog metadata plus bucket configuration and migration history; no customer/artist business rows or secrets were exported.

## 2. Approved product constraints carried forward

Primary control may be a person or organization, with one Primary Controller and independent revocable access grants. Multiple organizations/people can share an artist. Profile editing and finance are separate capabilities; managers receive no implicit finance permission. Payees must be explicitly provided records. Identity, representation, payout readiness and track rights are independent facts. Buyer trust uses its own public contract. Revocation preserves all business/history records. Primary transfer is protected and audited; disputes may freeze sensitive changes while retaining records. Sensitive audit records are not user-deletable.

These are accepted design constraints, **not implemented features** in this change. No organization/membership/invitation/payee structures or new Artist Desk UI were added. The existing buyer invitation table appears in fixtures solely because it is already in the repository migration chain.

`user_profiles.role` remains canonical; platform admin is not a team-manager role. Existing checks use verified auth users and database roles. Artist ownership remains `artist_profiles.user_id` / `tracks.artist_user_id`. There are no independent artist access grants or a catalog-only/finance split.

### Reproduced security gaps — not fixed in this phase

1. General artist-profile writer can set legacy `verification_status`. Live definition/grant evidence + isolated execution of the captured model establish the gap; no live verification row was changed.
2. Reviewed rights can be changed by the owning artist under production/repository rules without triggering parent review. Staging denies this. Draft `approval_status` still reflects self-declaration, not independent verification.
3. Buyer approved-track rows and the catalog serializer include full-audio storage path / internal account or reviewer IDs. **This is metadata exposure, not a demonstrated full-audio download bypass.** Private profile payout contact and rights-holder emails remain inaccessible through the tested buyer paths.
4. A distinct catalog-only/finance capability cannot be expressed. An existing artist owner legitimately has their own payout contact, but that broad grant cannot safely be reused for a contractor/manager. No claim is made that a nonexistent Finance role was tested.
5. Admin track/order actions query privileged context before their admin guard. They deny unauthorized mutation, but violate the required authorization-before-resource-access ordering. Agreement download also fetches generated-license metadata before ownership denial; signing/delivery is denied correctly. These are internal read-order findings, not proven forbidden response disclosure.
6. Actor/artist deletion can cascade business/history records; primary-transfer/revocation must never use account deletion.
7. The existing payout screen still derives a tax/entity display name from the stage name; this test-only phase does not change that UI or create payee records.

## 6. Account-deletion regression baseline

Live FK definitions confirm these paths; synthetic destructive tests ran **only in isolated memory**:

| Scenario | Current observed local replay outcome |
|---|---|
| Delete artist account with no orders referencing its tracks | Artist profile, tracks, rights, track options and track-bound audit can cascade away. |
| Delete artist account with a track referenced by an order | Track deletion is blocked by non-cascading `orders.track_id`; transaction fails and order survives. |
| Delete buyer account with order/license/activity | Order, generated license and order activity cascade away. |
| Delete actor account | `track_audit_log.actor_id`, `order_activity_log.actor_id`, optional rights-holder user and track approver use SET NULL; review-note author/admin-flag creator use CASCADE. Parent-track cascades can still remove history. |

Eleven application foreign keys are NOT VALID in both captured environments. This means old rows were not validated when those constraints were added, **not** that new writes bypass FK checks. No live orphan/customer-record scan was performed; additive-schema preparation must use approved aggregate integrity checks before validating constraints. The catalog baseline alone cannot establish all existing data conforms.

No account deletion endpoint was enabled or changed. Future revocation must update membership authority independently of account deletion, while preserving durable artist, order, license, rights, payee and audit records.
