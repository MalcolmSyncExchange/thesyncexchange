# Fresh upload initialization regression

Production evidence: draft `ba95d1a4-a390-4072-a0f6-bdd2d04ae1a8` was created and its blank workspace saved successfully, but there were no file reservations or stored source objects. Its preliminary waveform remained on-device. No records were deleted or rewritten during diagnosis.

The initial-file effect ran before the effect updating `latestUpload.current`. Its previous-render closure could have `data=null`; `mutation()` then supplied `revision:undefined`. `command()` refreshed the server revision only if an existing revision was defined, so the JSON request omitted the required revision. Executing that actual client command against the actual route validator reproduced `CHECK_REQUIRED_FIELDS` before rate admission or a reservation RPC. This is not a Track Details, preview acceptance, 150 MB, Storage, or worker admission failure.

The patch installs the current uploader before the initial-file effect. Every new keyed client command reads the current server revision after its existing draft-save flush; the database still performs the authoritative atomic CAS and ownership checks. Uncertain-response recovery bypasses preparation and retains the exact request/key, rather than creating another upload. Initial definitive errors offer a manual retry using the retained master File and preview state; ambiguous requests must recover first. Existing reserved transfers still use their existing resume path. Errors are described by request stage and file size. Final submission validation is unchanged.

No SQL, bucket, IAM, worker image, accounting, budget or admission changes. Rollback is the previous immutable Netlify deploy `6aff81a0d6cf6d9cbe3ecd2d`; it retains all data but reinstates the original initialization defect. Keep the founder's failed browser tab untouched while deploying, and use a separate synthetic 45.5 MB recording for fresh-path QA. Do not replace or remove the founder's selected recording to perform the test.
