## Authoritative chain

1. Artist `media_create_submission`, reservation, observed exact Storage identity.
2. Fenced technical validation, generated exact-source preview, Artist acceptance.
3. Canonical Admin `media_decide_master_review` approves a frozen package.
4. PK03 reviewed offer identifies both rights pools, evidence and legal parties.
5. `reserve_approved_source_delivery` reserves a commerce master from that precise
   READY media source. An explicit server command uses the bounded PK08 fetcher,
   validates original bytes, uploads without overwrite, reads/verifies destination
   bytes and atomically seals/links only while that source is still approved.
   Delivery MIME derives from the technically measured container, including
   generic MIME uploads. Unknown upload responses reread the same object; mismatch never seals and no
   orphan is deleted. Large copies require separately approved worker capacity;
   no HTTP endpoint or automatic copy execution is enabled.
6. `link_approved_delivery_source` explicitly reviews every sealed variant against
   that submission/master. Masters must match canonical object/version/hash/size.
   Non-master variants retain explicit Admin recording-association attestations;
   no automated derivation or stem identification is claimed.
7. PK08 `review_license_deliverables` specifies included versions per offer.
8. `review_purchase_source` freezes submission/master/review IDs, package and byte
   hashes, technical validator/build, catalog metadata, rights hash/generation and
   license manifest plus variant-source review references. It requires the exact
   expected submission revision and an explicit manifest, even if agreement-only.
9. Quote trigger runs after PK08's deliverable trigger, includes this evidence and
   hashes the complete schedule. Buyer sees the recording version/reference and
   exact included files before transaction-specific assent.
10. Acceptance, provider attempt, payment-fenced agreement publication and active
    entitlements all recheck original source evidence. PK07 verifies payment;
    success-page rendering never establishes payment. The generated agreement's
    existing full transaction appendix includes the frozen source evidence.
11. PK08 broker admits only the accepted entitlement, fetches sealed bytes, hashes
    them and rechecks current permissions immediately before release.

No new asset/submission table is invented. `source_asset_links` stores immutable
associations to existing media and commerce versions, not another byte registry.
`source_reviews` stores per-offer immutable approval evidence. `source_revisions`
provides monotonic compatibility fencing; `source_status_events` retains reasoned
restrictions. All four are private, FORCE RLS, no API/service/broker table grants.
Foreign keys retain canonical evidence. Review/link/restriction history is immutable.

## Compatibility and recovery rules

Pending/unissued purchases require the SAME current approved master/review and
source generation. Title, slug, seller, approval or legacy recording changes, and
canonical master activation, bump a generation; reverting cannot revive stale
assent. The user must review a newly approved offer/quote. Interrupted provider
operations keep their original PK07 key and original snapshot; no re-quoting or
silent pointer substitution occurs during recovery. Stale paid purchases retain
verified payment and require manual reconciliation/refund; no license is issued.

Already issued licenses retain their approved original package and copied assets
through later metadata/master replacement. Old approved technical evidence is
retained. Current rights validity, catalog approval, canonical identities, legal
usage expiry, refund/dispute holds, asset retirement, session revocation, private
object identity and source restrictions still gate access. A compatible source
replacement does not redirect historical downloads to the new source. Rights
amendments retain PK03's independent monotonic invalidation; this bridge cannot
waive those restrictions. An unavailable/mismatched/public source fails closed.

`restrict_purchase_source` is service-only plus canonical Admin verification,
serializes on the track, and appends a permanent restriction. No generic unrestrict,
source rewrite, automatic asset deletion, earnings correction or agreement
regeneration endpoint is introduced. Operator resolution is a later reviewed
workflow; the immutable record is available for investigation.

## Locking and security

PK03 serializes quote/issuance against the track. Canonical media Admin activation
locks submission then track before publishing pointers. Bridge readers lock the
track and read the immutable submission package without taking a submission row
lock; they never invert that order. Material source pointer writes lock the track
in the generation trigger. PostgreSQL tests observe real lock waits, stale assent
rejection and restriction-before-byte-release denial. Deadlocks/serialization
errors fail the transaction; an interrupted caller must reread its operation.

All new definers use empty search_path and qualified names. Six service-only
commands require canonical Admin authority before accessing private records;
source-chain reads require authenticated canonical Admin. Server adapters call
`requireSession('admin')` before creating the privileged client. No music-download
Admin bypass, arbitrary Storage path, client amount/party authority or secret is
accepted. The SEC order trace returns safe IDs/hashes/review facts, verified
payment states, original purchase hash, license and entitlements; no Storage paths,
tickets, provider keys or credential material. It is read-only and does not post
financial entries. Old no-source records remain retained and cannot be silently
adopted into the new issuance/delivery path.
