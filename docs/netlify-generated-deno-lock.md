# Netlify generated root Deno lockfile

Netlify CLI 27.12.0 successfully built the approved auth fix, then its
post-build clean-worktree gate rejected the new root `deno.lock` before upload.
The build log identifies the Edge Functions bundling phase, packaging
`___netlify-edge-handler-middleware` from `.netlify/edge-functions`.

The installed `@netlify/edge-bundler` invokes Deno while constructing its module
graph (`dist/node/formats/tarball.js`: `deno info --json --no-config --import-map ...`) and
warming Netlify types (`dist/node/types.js`: `deno cache -r`). Neither invocation
passes `--no-lock`. Deno discovers the project workspace and generates its root
lockfile. The observed version-5 file contains SHA-256 integrity entries for the
Netlify bootstrap modules and a workspace dependency inventory derived from
package.json. It is not empty or meaningless, but this application does not
maintain a Deno project or direct Deno dependencies: the file is generated by
Netlify's adapter packaging, not authored application dependency configuration.

Application dependency reproducibility continues to use committed package.json
and package-lock.json. Netlify-generated graph metadata can be regenerated by
edge bundling; it is not a prerequisite source input for the first build. The
root file may be retained locally for Deno's integrity checking. No file is
automatically removed. If direct Deno application dependencies are introduced,
revisit this rule and deliberately validate/version the relevant lockfile.

Handling rule: `.gitignore` contains exactly `/deno.lock`, with a comment linking
this receipt. It affects only the generated repository-root file. Nested
`deno.lock`, npm lockfiles, all other untracked files and modifications to tracked
files remain subject to the existing publication clean-worktree checks. Even a
root deno.lock, if deliberately tracked later, remains subject to those checks.

Publication scripts are unchanged. Exact commit checks, clean-source checks
before and after build, staging identity and credential checks, analytics/payment
gates and SHA-256 fingerprints of `.next` and `.netlify` all remain mandatory.
The ignored graph metadata is outside the uploaded build output; its presence
does not change those fingerprints. Actual packaged edge/functions artifacts
remain covered by the existing fingerprint.

Regression tests use an isolated real Git repository to demonstrate the exact
ignore scope, blocked unexpected files and tracked edits, unchanged source
commit/tree and artifact fingerprints, alongside existing wrong-site, disabled
analytics/payment, changed-artifact and CLI-combination tests.

No hosted changes, upload, signup, email, payments or database actions are needed.
The offline checked-wrapper dry run validates installed CLI arguments and local
site selection with upload disabled; hosted credential gates must still pass in
any separately authorized real publication.
